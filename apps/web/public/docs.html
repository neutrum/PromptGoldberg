Prompt Goldberg

One sentence makes a level. Someone else solves it.

Type any idea, in any language: “a taxi ball crosses New York and stops at the Statue of Liberty”. In seconds the AI turns it into a 3D physics level: the world, where the ball starts, the goal, a landmark that belongs there and the obstacles in the way. Then a person solves it, placing ramps, fans and cannons by clicking or by saying where they go, and pressing Run. The AI sets the stage; it never plays the game for you.

Try it in a minute

  1. Start with level 1. One ramp in your tray, twelve dominoes and a bell: find where the ramp goes (click the stage, or say it in the Build box, e.g. put a ramp next to the ball) and press Run. The levels give no hints: they are yours to crack.
  2. Make a level. On the start screen (🎮 Levels), type anything: a place, a story, three emoji, a sentence in Slovak. You are its designer: say build a fence around the goal, make it night, or make a new part on the Workbench (a spiral chute).
  3. Test it as a player, then Send to a player: the whole level travels in the link.

Stuck for ideas? 💡 Prompt ideas (top left in the game) shows twelve levels the AI made, with the sentence that made each.

Why it matters

Making a game level has always meant learning a level editor. Here the editor is a sentence, and the game is still a game: the AI is the level designer, a person is the player. Every level is a physics puzzle the AI proves can be solved with the player's own parts, but it never solves it for them unless asked, and then without stars.

  • Players get endless puzzles in worlds they ask for, from the Eiffel Tower to a messy kid's bedroom.
  • Creators make a level in a sentence, refine it in more sentences and share it as a link; new parts come from the Workbench, with a 3D model: a few free ones a day on the server, or any number on their own 3D model key.
  • Teachers get cause and effect you can see, on real rigid-body physics.
  • VR and the metaverse: a level is plain, validated JSON (MachineSpec), so another front end, a VR world or a mobile app, can play the same levels through @pg/client and @pg/game.

What makes it general rather than a set of templates:

  • No hard-coded worlds. The AI writes the world (palette, features, obstacles, a landmark) for whatever the sentence names; keyword worlds exist only as an offline fallback.
  • A library of 503 things (animals, vehicles, buildings, food, about sixty landmarks), each a shape recipe composed once by the AI and reviewed, found by words with no AI call; 108 have 3D models.
  • New parts on demand. The Workbench builds a part from a description; its boxes collide, so it works in the physics. Every part made is kept and reused without another AI call.
  • Bring your own AI. Settings → AI providers: Claude, ChatGPT, any OpenAI-compatible service, Tripo or Meshy. A new provider is one file.
  • Words for what the player does, read instantly with no AI call: add a fan 3 cells east of the ball, turn the fan to face south, put the spiral chute next to the taxi, remove + a click, make it night.

How it works

  1. One AI call per level. The AI answers with a small route graph (the level idea), streamed so the world appears while the rest is laid out.
  2. Layout without AI. layoutLevel places the start, the goal across the board, the named things and obstacles in the way, keeps a floor path open, and makes sure the level does not solve itself.
  3. Fairness proof. solveWithKit, a beam search over placements along the ball's path, simulated in a physics worker pool, looks for a build from the player's own tray that reaches the goal. The solution is never shown; it only proves one exists.
  4. Play. Rapier physics (deterministic) runs in a browser worker. When the player wins, the server runs the same build and compares the trace hash: ✓ server agrees.
  5. Solve on request. Only when the player asks, the AI looks for a way through by adding parts; no stars for that one, and an honest miss when it finds none.

Architecture

A layered TypeScript monorepo. Lower layers never import upper ones, and only the programs touch a framework (React, Fastify) or a platform (DOM, storage, Node workers). The game is one user of the engine; the command line is a second.

One level, end to end

AI providers, the Workbench and 3D looks

  • Providers (packages/ai/src/providers): text providers (Claude, OpenAI, any OpenAI-compatible endpoint) and mesh providers (Tripo, Meshy) in one registry. The server uses its own Claude unless a request carries a player's provider and key in headers; those are used for that request only and never stored or logged. Adding a provider is one file and one line.
  • Workbench: a new part from a description, built from a few boxes, cylinders and spheres; its boxes collide, so it works in the physics. Boxes can slope and turn, so a part can steer the ball: a spiral chute takes it round a post. A shape can also spin (a sweeper arm, a paddle wheel): the physics turns it at a steady rate, it pushes the ball, and the replay turns it the same way. Every new part goes through the test lab (a ball dropped on it in the physics, or rolled into a spinning one) and gets one more AI try, told what the ball did, when it does not get through. Every part made goes into a shared library; asking again by its name returns the kept part with no AI call, unless the ball does not get through it, then it is made again.
  • 3D looks: a mesh provider makes a model for a Workbench part (the player's own key, or the server's for a few a day; off until the player ticks the Workbench's 🎨 toggle); the server downloads it only from the provider's own hosts, shrinks its textures to 512 px, keeps it under its hash and attaches it to the part. The shapes stay the colliders; the model is only what is drawn.
  • The library: 503 things, each a shape recipe composed once by the AI and reviewed; 108 have low-poly Tripo models made once (scripts/pregen-library.ts).

Failsafes

SituationWhat happens
The AI's answer is invalidChecked before anything changes (schema, the level's own rules); retried; then “The AI could not make that work this time. Nothing changed”.
An AI change is slowA few small edit operations on a fast model, up to three tries (a full rewrite of a big level would not fit); the whole change stops at 25 s (EDIT_DEADLINE_MS) and the level stays as it was.
Common requestsLooks (“make it night”, “snowy”, “sunset”), placing, turning and removing parts, adding named scenery: no AI call at all.
The Workbench AI failsThe closest known part, after at most a minute.
The Workbench part fails the test lab twiceA known part of that kind that passes (spiral chute, spinner, chute, ski jump, bumper, gate), with a note.
A level the solver cannot proveStill playable, marked unproven; “Solve it for me” says when it finds no way.
SpendingA daily AI-call cap kept on the data volume (a redeploy does not reset it), per-IP rate limits; a player's own key is outside the cap.

API reference

Base URL: https://ogserver-production.up.railway.app. JSON in and out. Errors are { "error": "…" } with a 4xx or 5xx status. The typed client for every route is @pg/client.

Levels, streamed

These answer with server-sent events (text/event-stream): progress while the AI works, then one final machine or error event.

RouteBodyDoes
POST/api/machine{ prompt, stage? } prompt up to 500 characters; stage { x, z } in cellsA new level from a sentence. Without an AI on the server, a level from the sentence's keywords.
POST/api/machine/edit{ machine, instruction } instruction up to 300 charactersA change to a level in words; stops at 25 s.
POST/api/machine/solve{ machine }Only on request: a way through, first by physics search with the player's kit (no AI), then by the AI adding parts.
event: world    { "type": "world", "landscape": { "name": "New York harbor at dusk", "sky": "#…", … } }
event: stage    { "type": "stage", "stage": "verifying", "message": "Checking a way through exists with the player's parts." }
event: machine  { "type": "machine", "machine": MachineSpec, "solved": true, "verified": true, "attempts": 1, "notes": […] }
event: error    { "type": "error", "error": "That change took too long. Nothing changed: try again, or say it in fewer words." }

Other events: progress (search progress), sketch (parts as they are placed), draft (a candidate level).

The level format

A level is a MachineSpec, validated with zod in packages/core/src/schema.ts:

{
  "title": "Taxi to Liberty",
  "landscape": { "name": "New York harbor at dusk", "sky": "#…", "features": [ … ], "landmark": { … } },
  "terrain":   [ { "name": "river", "x": 6, "z": 0, "w": 2, "d": 24, "h": -1 },
                { "name": "red carpet", "x": 2, "z": 18, "w": 8, "d": 2, "h": 0, "color": "#b01e23" } ],  // with a color: a flat surface, looks only
  "parts": [
    { "id": "ball",  "kind": "ball",  "label": "taxi",              "x": 2,  "y": 5, "z": 5, "yaw": 0 },
    { "id": "goal",  "kind": "bell",  "label": "Statue of Liberty", "x": 20, "y": 0, "z": 18, "yaw": 0 },
    { "id": "rock1", "kind": "wall",  "prop": "rock", "fixed": true, "x": 9, "y": 0, "z": 9, "yaw": 0 }
  ],
  "spares": [ { "kind": "ramp" }, { "kind": "fan" } ],
  "goal":   [ { "type": "bell", "part": "goal", "times": 1 } ],
  "duration": 15
}

Parts: ball, ramp, platform (shelf), wall, dominoes, seesaw, fan, trampoline, cannon, bucket, bell, and coaster track (track, curve, descent, ascent); a cell is 0.5 m; yaw is 0, 90, 180 or 270.

Run it yourself

npm ci
cp .env.example .env    # LLM_BACKEND=cli uses your local Claude Code login; production uses ANTHROPIC_API_KEY
npm run dev:server      # API on :8787
npm run dev             # the game on http://localhost:5173
npm test

# The engine without a browser
npm run pg -- level "a snowball races down the High Tatras into a mountain hut" --out tatras.json
npm run pg -- play tatras.json "put a ramp under the snowball" "add a fan 4 cells east of the snowball"
npm run pg -- judge --server https://ogserver-production.up.railway.app --only tokyo,slovak,emoji

Deploying: one Docker service (Railway), with a volume at /data for community levels, daily boards, the Workbench library and 3D models.

Honest limits

  • One ball per level; a run simulates 15 seconds by default (30 at most).
  • A themed thing is a themed part: a pizza is a named ball, an oven a named bucket. The physics is the kit's.
  • “Fair” proves one build works with the tray; it does not prove a level is fun or easy.
  • Most world things are shape recipes; 108 have 3D models.
  • ChatGPT and Meshy support is marked experimental: built and unit-tested, not run end to end.
